# Dungeon first-entry evidence (PR #264)

- Scope: six unchanged A/B/C × short/long journeys, 256 seeds per policy, 100 first physical entries per completed owner (153,600 rows).
- `FIRST_ENTRY` is captured in `simulate-dungeon-journeys.mjs` in the existing layer loop **before its first `battle()`**, and is write-once even after defeat, return, or replay. The snapshot contains the in-sortie HP/MP, equipped five circles, current individual carried items, committed/uncommitted resources, legal start ranks, and the first fight index.
- First-entry snapshots explicitly say `NOT_ASSESSED_AT_FIRST_ENTRY`. They do **not** call or substitute for the official `assessRecommendedStrength` calculator, whose later post-return firstReached evidence remains unchanged in the ten-band audit. The full record retains independently linked reaching event counts; a later reach must never be interpreted as a passing assessment of an earlier entry.
- `dungeon-journey-strength-v2.json` indexes six separate `dungeon-first-entry-v1-A-short.json`–`C-long.json` evidence files. Each contains first-entry snapshots, combat floor receipts, sortie completion/count ledgers, and separate official reached-event links. The strict checker loads one policy at a time and uses original first-decade snapshots, simulated combat floor audit receipts, inventory instance/usage accounting, legitimate invested stones/ink, rank release and chronological return/battle counts to test integrity.
- Mandatory gate: 153,600 physical and legal first-entry records **plus** the existing formal 15,360 reached outcomes, 1,536 clear records, chapter criteria and fixed-deck results. Merely challenging below recommended strength never fails.
- Limits: the historical original 10-band calculator evaluates banked and invested readiness snapshots, not every physically exhausted first-entry state. No unassessed state receives an invented recommendation score. The audit establishes consistency with genuine simulation histories, not a cryptographically independent recording of live human gameplay.
- Validation: GitHub Actions `dungeon-regression-suites` runs nine mutated-evidence failures, legal post-defeat recovery, and observational balance invariance; `dungeon-journey-strength-strict` checks all six independently sharded policy files without skipping entries. Neither process changes the actual battle or economy algorithms.
